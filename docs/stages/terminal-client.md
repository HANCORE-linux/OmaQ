# Terminal client: omaq-connect

**Status:** done; ships with 1.0.0; extended in 1.1.0; transfer fixes in 1.1.1; recall fix in 1.1.2.
**Date:** 2026-10-10

`omaq-connect` is a text-only OmaQ client for any terminal. It is one more client of the helper socket beside the bar, so the bar and its behavior stay unchanged.

## Landed

- `cli/omaq.py` with the `cli/omaq_connect/` package, Python 3.11 or newer, standard library only. It speaks the helper's JSON-line protocol on `$OMAQ_STATE/omaq.sock` exactly like `Service.qml`:
  - **Handshake:** `status` with a nonce, and a snapshot correlated by `request`.
  - **Protocol gate:** Protocol 16 or newer.
  - **Key binding:** every direct operation carries the stable `key`, and direct events whose `key` does not match the friend are dropped.
- **Usage:**
  - `omaq-connect` opens the chat with the first friend; `omaq-connect <name>` opens it with that friend.
  - The friends bar shows online (green), AFK (amber) and offline (gray) dots. Names longer than 18 columns end in `…`. Friends that no longer fit are summarized as `+N`, drawn in the unread color when one of them has unread messages. A friend with unread messages whose chat is not on screen gets a name filled in the unread color until the chat is read; there are no numeric badges. A new message from a chat that is not on screen also shows its first line in the status line for 8 seconds.
  - Each pane header shows `online`, `typing…` or `offline` beside the name. The focused pane's header starts with `❯`, and the input line shows the chat partner's name on an accent background, followed by `❯`.
  - Own messages end in a compact receipt that never regresses: `·` sending, `→` sent, `⇉` delivered (dim), `⇉` read (green, bold). A failure shows `✕` and the bar's failure text. `:help` lists the receipt legend.
  - Every message shows only `HH:MM`. A dim divider (`── today ──`, `── yesterday ──`, `── Thu 8 Oct ──`, with the year when it differs) marks each new day.
  - **Replies:** `ctrl+r` (or `:reply`) marks the newest message that can be answered with an accent `▌` and shows `↑/↓ choose · enter reply · esc cancel` on the bottom line. `up`/`down` (and `ctrl+r` again) step to older or newer messages, `pgup`/`pgdn` by five, `home`/`end` to the oldest or newest loaded one; the chat scrolls to keep the mark in view, and incoming messages leave the position alone. `enter` or `r` picks the message: `↩ Reply: <preview>` appears above the input line, and the next message carries its id as `msg.send` `reply`. Pasted text and any other key end the choice and go into the draft, so a paste never picks a message. Only messages with a helper id can be answered: no system lines, unsent, failed or local items, deleted messages, files or images, whose ids differ between the two sides. The choice belongs to the message id in that chat; switching the pane's chat, a rebound number, a cleared chat or an identity change drops it.
  - A message that answers another starts with `↩ <preview>` in the accent color when the quoted message is loaded, as in the bar; otherwise there is no quote line. The preview follows the bar's `compactReplyPreview`: whitespace collapsed to single spaces, at most 120 grapheme clusters, then `…`. A unit test pins the rules, and a one-off comparison with `MessageLayout.js` matched all 3005 generated texts. A quoted message that was deleted reads `Message deleted`.
  - **Edits and deletes:** the helper's `message.updated` changes a loaded message at once. An edit shows the new text with a dim `(edited)`; a delete shows `Message deleted`, as in the bar. History items carry the same `edited` and `deleted` flags. A reply in progress to a message that gets deleted ends with `Reply canceled: the message was deleted`.
- **Split views:**
  - Panes are arranged in columns. `:connect <name>` (or `ctrl+n`) opens a pane on the right, `:split <name>` opens one below.
  - `alt+arrows` (also `alt+h/j/k/l`) move the focus, `alt+shift+arrows` move the pane, `alt+=`/`alt+-` resize the column, and `tab` switches the pane's chat.
  - Too small a terminal shows one pane with a tab strip.
- **Commands:**
  - `:quit` (also `:q`) quits OmaQ, `:close` (also `ctrl+w`) closes the pane.
  - `:help` (or `F1`) lists the commands to select with the arrow keys.
  - In a window too small for the content, `:help` and the invite and request views scroll. The first and last rows then show `↑ N more · pgup` and `↓ N more · pgdn`, `pgup`/`pgdn` turn the page, and the selected command stays visible. Enter on a selection that paging moved out of view only scrolls back to it. Below three rows there are no markers.
  - `ctrl+c` clears the draft and shows `Type :quit and press Enter to quit`; it never quits.
  - `esc` first ends a reply choice, then drops the chosen reply, then clears the draft, and on an empty line hides a file notice.
  - `up`/`down` browse this chat's own text messages, newest first, including unsent and failed ones, so they never cross into another chat. File and image items are skipped, so their local paths never come back into the input line. After `:` they browse earlier commands. Going below the newest entry restores the draft that was there before. Recall ends when the chat's number moves to another contact, and an identity change also clears the command history.
  - `:clear` asks `Clear this chat? y/n` for 15 seconds. The prompt keeps the status line until it is answered or expires, and other notices wait behind it, so a prompt that is not on screen never consumes a key. It is bound to the contact's stable key and the helper instance: a rebound number, an identity change, a lock or a dropped connection cancels it with `Chat kept`, and `y` sends the confirmed key, which the helper checks again. Notices that arrive while the prompt is shown do not expire behind it; after the answer they appear together with the result, such as `Chat kept · An item could not be added to chat history`. On `y` it sends the request-correlated `history.clear` like the bar's Clear chat (only with `historyClear` 2 in the snapshot). It removes this conversation's history on this computer only; the helper also clears its unread state. The result (`history.clear.succeeded`/`failed`) is matched by request, key and helper instance, as in the bar. An open bar chat window ignores this foreign result until it is reopened.
  - The bottom line keeps `:help` and `:quit` and shows one short tip beside them, such as `ctrl+k opens the emoji picker`. The 23 tips cover the other commands and keys; one changes every 8 seconds while the terminal has focus and no command is being typed. When the line gets narrow, the tip goes first, then the text size; `:help` and `:quit` stay. Typing `:` turns it into filtered suggestions with the selection highlighted. `tab`/`shift+tab` cycle commands, and friend names after `:connect`/`:split `; after `:sendfile ` `tab` opens the file list. A unique prefix runs its command (`:he` opens help).
- **Friends:**
  - `:invite` sends `invite.create` (direct, 24 hours) like the bar's invite page. It shows the link and a QR code drawn by `/usr/bin/qrencode -t UTF8` (the link follows `--`). With an Omarchy theme the code is truecolor white on black, so a theme's palette can never invert it. The validity countdown refreshes every minute and then shows that the invite expired. The link goes to the clipboard through OSC 52, which the terminal handles, also over SSH. An active, unexpired invite is shown again instead of being replaced. `:invite revoke` asks `Revoke this invite? It cannot be used again. y/n`, the bar's wording, and sends `invite.revoke`.
  - `:redeem <omaq:// link>` sends `invite.redeem` with a request id; links over 511 bytes, the helper's payload limit, are refused locally. `invite.redeemed` shows the bar's result ("Invite checked. Waiting for the other person to accept." or the group variant) and the safety code the friend will see.
  - Errors use the bar's wording, such as "That is not an OmaQ invite.". The helper broadcasts uncorrelated errors to every client, so the CLI shows one only within 10 seconds of its own invite, redeem, accept or decline; errors caused by the bar stay in the bar. An error that carries another client's request id or a conversation never counts, and the window closes once the CLI's own action has its result.
  - `:accept` and `:decline` send `contact.decide` with the CLI's own request id. The helper ends every decision with `contact.decided` (`request`, `ok`, and `code` on failure). The CLI reports that result, which also corrects a status that an uncorrelated error from another client overwrote. Older helpers fall back to the 10-second window. A failed send says "Not connected" or "Could not send the request".
  - A pending request (the `request` event, which every `status` repeats) shows `1 request` or `1 group invitation` at the front of the friends bar. `:requests` shows it with the safety code ("Compare this code with your friend before accepting"), wrapped by whole four-digit groups in a narrow window with a blank row between the halves (explanations wrap as well), and the bar's `request.conflict` warning "Another device used this invite link".
  - `:accept` and `:decline` send `contact.decide`, with the request key for a direct request, like the bar. A direct request disappears when the helper clears the invite; a group invitation disappears at once. Both commands need the full word. The bar still sends the fixed id `x` and ignores `contact.decided`.
  - Group invitations can be accepted, but group chats stay in the bar for now.
  - `:nickname <name>` sends `nickname.set` with the CLI's own request id, like the bar's nickname field. The name is checked first as in the bar (1–18 characters, no control characters), and the helper keeps the final say. `:nickname` alone shows the current name, which arrives with every snapshot and `nickname` event. Results use the bar's wording, such as "Nickname must contain 1–18 valid characters." or "Nickname saved; group updates are unconfirmed."; without an answer within 10 seconds the client says "Nickname update timed out. Try again.". The command needs the full word.
- **Files:**
  - `:sendfile <path>` sends `file.send` (kind `file`) with the friend's stable key. Relative paths, `~` and quoted paths work. A file over 8 MiB, the helper's `OMAQ_FILE_MAX`, is refused before sending with `Files can be at most 8 MiB`; a unit test keeps both limits equal. A path that is not valid UTF-8, or a relative path after the working folder was deleted, gives a status message.
  - `tab` after `:sendfile ` (or an abbreviation that runs it) opens the file list above the input line; the path stays in the line. It lists the folder of the typed path: folders first, then files with their size, sorted by name. Typing filters by the start of the name; names starting with `.` appear once the typed name does, and names that are not valid UTF-8 or contain control characters are left out. `up`/`down` choose and `pgup`/`pgdn` page, `tab`, `right` or Enter open a folder or take a file into the line, `left` or `shift+tab` first drops the typed name and then goes up a folder with the previous folder selected, and `esc` or `ctrl+c` closes the list. Taking a file does not send it; the next Enter does. Enter with nothing to take runs the line as typed, and the hint says so. A name taken from the working folder gets `./` in front, so a name that starts with a quote, a space or `~` keeps its meaning; a path that starts or ends with a space is quoted, because the command line is stripped. A quoted path is read without its quotes. A missing, deleted or unreadable folder says so in the list. The list reads at most 50000 entries of a folder and says so when there are more. It only takes an entry it shows: an overlay closes it, and when the window has no room for an entry, Enter runs the line as typed.
  - The client first checks for a readable regular file and a path of at most 511 bytes, the helper's field limit. The helper keeps the final say.
  - One transfer per chat, as in the bar ("A file is already sending"). `file.sending` supplies the transfer id. `:cancelfile` sends `file.cancel`, and waits for that id if it has not arrived yet. It also cancels an accepted incoming transfer, which the helper confirms with `file.canceled`, and declines a pending offer; without a transfer it says `No file transfer in this chat`.
  - A `file.offer` bound to the friend's key is held per chat together with that key; a second offer is declined, as in the bar. The chat shows `⇣ File offer: name (size)` with `:acceptfile or :declinefile`, the status line names the sender, and a friend whose chat is off screen is highlighted.
  - Incoming files stay paused until accepted. `:acceptfile` sends `file.accept` without a path, so the helper picks its default folder: `$OMAQ_DOWNLOAD_DIR/omaq` or `$XDG_DOWNLOAD_DIR/omaq`, else `~/Downloads/omaq`. The status line shows the saved path. `:declinefile` sends `file.cancel`. Both act only on the focused chat. If the helper cannot open the download, it cancels the transfer and sends `file.failed` with `accept_failed` for that transfer id and key (`transfer_unknown` when the offer no longer exists), so the offer goes away instead of waiting forever.
  - Results (`file.done`, `file.failed`, `file.canceled`) are matched by request or transfer id and key, and use the bar's wording. After a transfer the chat reloads its history. `File transfer successful` stays for 7.5 seconds; warnings stay for 15. A cancellation by either side also leaves `✕ File transfer canceled: name` in that chat, bound to the contact's key, like the bar's dismissible file status. `Esc` on an empty input line hides it, and a new offer or send, another result, or a rebound number replaces it. If the helper then cannot save it to history, its `history_failed` error for that chat adds the bar's "An item could not be added to chat history" to the result.
  - A dropped connection keeps offers and transfers. After the next handshake with the same helper instance, each outgoing transfer is checked with `file.status` and a cancel that was waiting for the transfer id is still sent, as in the bar. A restarted helper ends them with `File transfer failed: helper_restarted`, and a rebound number drops them.
  - Incoming offers are checked too. `file.status` with a transfer id (`F:N`) instead of a request id returns `file.state` for that incoming transfer: `offer` with name and size, `receiving` with `done` and `size`, or `unknown`. Until the answer arrives the chat shows `checking…`, and such an unconfirmed offer never makes the client decline a new one. An `unknown` answer drops the offer with "File transfer status unknown; check the chat".
  - When the peer cancels a transfer, the helper now only drops its local state. It used to answer with its own Tox cancel; toxcore runs the callback before freeing the slot and answers controls for missing transfers with another cancel, so that echo killed the next transfer that reused the slot.
  - The helper reports `file.progress` (`done` and `size`, direct transfers only, never avatars) at most every 250 ms and only when the percentage changes, so at most about 100 events per file. That rule is `omaq_file_progress_due()` in `file.c`; its state is cleared when a transfer ends, so a transfer that reuses the numbers starts fresh. `tests/file_transfer_test.c` checks it without network or toxcore. The chat line then shows a bar such as `Sending notes.pdf  ███████░░░ 70%` or `Receiving …`. When a transfer line does not fit its pane, the file name is shortened with `…`, and the bar, the size and the command (`:cancelfile`, `:acceptfile or :declinefile`) move to their own lines, so none of them is cut off. A label too long for the pane, such as `File transfer canceled:`, wraps, and the name gets its own line. Transfer lines stay at the bottom of their pane while the chat scrolls, and the receiving line names `:cancelfile` too. Events must match the transfer id or request and the friend's key.
- **Emoji:**
  - `:)` `:D` `;)` `:(` `:'(` `:P` `;P` `:O` `:*` `:/` `:|` (also with a `-` nose), `xD`, `^^`, `<3` and `(y)` become 🙂 😀 😉 🙁 😢 😛 😜 😮 😘 😕 😐 😆 😊 ❤️ 👍.
  - An emoticon converts only when it stands alone and a space or a new line follows; on Enter the whole message is converted. Links such as `https://` stay intact.
  - A draft that starts with an emoticon is a message, not a command; command lines are never converted.
  - `ctrl+k` opens a picker above the input line with the same emoji as the bar's composer picker (`composerEmojiSet` in `pages/ChatPage.qml`: the 22 reaction emoji followed by 🤟); a unit test keeps both lists equal. Arrows choose, Enter inserts at the cursor and Esc closes. Typing searches the English Unicode names of the single-code-point wide symbols in the emoji ranges (U+2300–23FF, U+2600–27BF, U+2B00–2BFF, 〽 ㊗ ㊙ and U+1F000–1FAFF), such as `fire` or `star`.
  - At startup the client measures how the terminal draws `❤️` (U+2764 U+FE0F) and a ZWJ sequence with two cursor position reports (`CSI 6n`), and adopts both widths. Alacritty draws `❤️` in 1 column, while Ghostty, foot and kitty use 2 and draw ZWJ and skin-tone sequences as one 2-column cluster. Without an answer within 0.3 seconds, U+FE0F counts as 2 columns and ZWJ sequences per code point. The cursor, backspace and delete step over whole drawn characters: a character with its zero-width followers, and ZWJ and skin-tone sequences where the terminal draws them as one cluster.
- **Text size:**
  - The terminal owns the font size, so the CLI never changes it. `ctrl+=`/`ctrl+-` (kitty: `ctrl+shift+=`/`ctrl+shift+-`) zoom the terminal, and `:help` names the keys for the terminal it runs in.
  - The client derives the cell height from the terminal's pixel size (`TIOCGWINSZ`, `ypix // rows`). The size at start is 100%. Only after a zoom does the bottom line show the new size at its right end for 4 seconds, such as `Text 112%`: in the accent color, or dim when back at 100%. It gives way while a command is typed and when the line is too narrow.
  - The probe found pixel sizes in Alacritty, Ghostty, foot and kitty. A terminal that reports no pixels shows no size.
- **Read state:** panes that actually show message rows are marked read with `conversation.read`, and only while the terminal has focus (focus reporting `CSI ?1004`). A header-only pane never counts. Unread state stays helper-authoritative, so the bar follows.
- **Stable identity:**
  - Drafts belong to the contact's stable key, not to the pane, so `tab` never carries a draft to another friend.
  - When a Tox friend number is rebound to a different key, its history, unread state, in-flight sends, file offers and transfers, a pending clear confirmation and the input recall are purged, as the bar's `purgeReboundConversation` does, and a pane follows the contact to its new number.
  - Every handshake sends `identity.ready` with the instance, as the bar does, so the client keeps working after an identity import, which resets every client's readiness. `identity` `import`/`recovered` events and a snapshot for a different public key (the first 64 hex digits of the address, as the bar compares them) rebuild the client state; a new nospam alone changes nothing. An `identity_changed` error, which the helper broadcasts to every client, only re-handshakes and reloads the histories; panes and drafts stay, as in the bar.
- **Reconnects:** a dropped socket marks every loaded history stale and every in-flight send `delivery_unknown`, as the bar does. After the next handshake every open pane reloads its history. Messages with unknown delivery, failed messages and messages that were sent but not saved stay in the chat after the reloaded history, as in the bar, and are never sent again. `message.failed` with `delivered:true` marks the message as sent and adds the bar's line "Message sent, but could not be saved locally.". `history.failed` retries after 3 seconds. A message that waits in the helper for a secure session belongs to the connection that sent it: when that connection drops, the helper discards it, so it is never sent behind the client's back.
- **Typing:** `typing.set` while composing, with idle and send stops.
- **Locked identity:** a hidden passphrase prompt sends `identity.unlock`; a wrong passphrase reports the bar's wording. The prompt accepts at most 128 bytes and a tab, and refuses pasted text with a line break or other control characters with `Enter the passphrase as one line` instead of joining the lines. A terminal without bracketed paste delivers a pasted line break as `enter`. On a passphrase line, an `enter`, `esc`, `ctrl+c` or `ctrl+d` followed by more input in the same read (focus reports and further line breaks do not count) is refused the same way: the line stays open and the rest of that read is dropped. When a passphrase line closes and no other passphrase line follows, whether by `enter`, `esc`, a disconnect or an identity change, or when the identity is unlocked by this client or another one, the client drops the rest of that read and discards all input until the terminal has been quiet for 0.3 seconds; an escape sequence that is still incomplete then is dropped when it completes, together with the bracketed paste it starts, and a bracketed paste that is still running is dropped whole. A lone `esc` that nothing follows counts as a key press and is dropped with the rest, unless a paste is still running, where it may start the end marker. Focus reports still count, so a window switch in that time is not lost. While a passphrase line is open, a piece of the paste start marker (`ESC [`, `ESC [2`, `ESC [20`, `ESC [200`) is kept instead of being flushed after 30 ms, so a paste whose start marker arrives in pieces cannot turn into typed text when the line closes from outside; the next key completes such a piece. The parser never flushes during a running paste, so an end marker that arrives in pieces still ends it, and a sequence broken by a byte that cannot continue it (`esc`, a control character, `DEL` or non-ASCII) is dropped and parsing restarts at that byte. Terminals with bracketed paste mark every paste, so pasted text never reaches the chat input there. Without it, typing and pasting look the same: a pasted line that arrives more than 0.3 seconds after the previous input still reaches the chat input. A send without a connection says `Not connected`, and a dropped connection or an identity change clears what was typed.
- **Identity:** `:identity` says whether the identity has a passphrase (the snapshot's `protected`, kept current by `identity` events from any client). The actions need the full words, so `:i` still opens `:invite`; `tab` completes them. Every change asks `y/n` right before it is sent; a passphrase waits only inside that question and is dropped with it on any other key, after 15 seconds, on a disconnect, or when the identity changes or locks. A lock also closes an open passphrase line, and a passphrase line drops a question that is still waiting.
  - `:identity protect` asks for a `new passphrase` and to `repeat passphrase` in a masked line (`•`, `enter continues · esc cancels`), checks the bar's rule first (at least 8 characters and at most 128 bytes, no control characters except tab; "Use at least 8 characters and at most 128 bytes."), asks `Protect your identity? This passphrase cannot be recovered if lost. y/n`, and sends `identity.protect`. Two different entries say `Passphrases do not match.` and send nothing. With a passphrase already set it refuses and points to `:identity unprotect`, as the bar offers only Remove lock then, and it also refuses while the state is not known yet; the client never chains unprotect and protect. It checks the state again after the repeated entry and after `y`. The helper also refuses `identity.protect` with `forbidden` while a passphrase is set, so a passphrase set meanwhile, for example in the bar, is never replaced; the client then says the identity already has a passphrase.
  - `:identity unprotect` refuses while the state is not known yet, asks for the `current passphrase`, then `Remove the identity passphrase? The identity is then stored unencrypted. y/n`.
  - `:identity export [path]` writes the bundle to an explicit absolute path: without a path, `$XDG_DOWNLOAD_DIR/omaq-identity.save` or `~/Downloads/omaq-identity.save` as in the bar; a folder gets that file name. It always asks first (`Export your identity to <path>? y/n`, or `Replace <path> with your identity? y/n` when the file exists). The result names the path and says to transfer the bundle securely and delete extra copies, and that it has no passphrase when the identity has none.
  - `:identity validate <path>` sends `identity.inspect`; `:identity import <path>` asks the bar's question `Import <path> as the active identity? Existing direct contacts will require a fresh invite.` and sends `identity.import` with `replace`. When the helper answers `identity_passphrase_required`, both ask for the `bundle passphrase`; validate sends once more, and import asks its question again before it sends once more. A wrong one reports `Identity file or passphrase is invalid.` and is never retried on its own. A successful import resets the client like an import from the bar.
  - `tab` after `:identity export `, `validate ` and `import ` opens the file list of `:sendfile`.
  - Passphrases never become command arguments and never reach drafts, recall or the command history; raw lines that arrive in one burst are refused as on the locked prompt. Each action has its own request id; results and errors of other clients only update the protection state. One identity action runs at a time, and after 20 seconds without an answer the bar's `The identity action timed out. Check OmaQ status and try again.` appears; a late answer is ignored. A dropped connection, or an identity change by another client, ends a running action with `Identity action result unknown. Check OmaQ status and try again.`.
  - Errors use the bar's texts. A `forbidden` answer to protect, which the local rule check makes a save failure, reads `The passphrase could not be saved.` instead of the bar's rule text, or `Your identity already has a passphrase; :identity unprotect removes it first` when another client set one meanwhile.
- **Narrow panes:** a pane too narrow for the time-and-name prefix shows that metadata on its own line and keeps the message body. Names are shortened with `…`. The single-pane tab strip keeps the focused tab visible.
- **Cursor:** the client asks for a blinking block (`CSI 1 SP q`); the terminal keeps it steady while typing. Exit resets it to the terminal's configured style (`CSI 0 SP q`).
- **Cleanup:** terminal restoration runs in an unconditional `finally` with SIGTERM, SIGHUP and SIGINT blocked during cleanup, and it closes synchronized output (`CSI ?2026l`).
- **Untrusted text:**
  - Peer messages, names and senders pass through `clean()` before reaching the terminal. C0 controls become control pictures, DEL becomes `␡`, and C1 and bidi controls become U+FFFD.
  - The helper itself rejects ESC/C0 in message bodies (`message.c`) and filters names with `omaq_group_member_name_bytes_ok`. `\r`, DEL, C1 and bidi controls in bodies still pass, which is why `clean()` is needed.
- **Outgoing text:**
  - It is limited to 511 bytes, the size of the helper's `omaq_op.text`.
  - It is serialized with raw UTF-8, because the helper JSON parser accepts only `\n`, `\t`, `\"` and `\\` escapes.
- **Colors:**
  - With Omarchy, the bar's System roles come from `colors.toml` in truecolor (name `color03`, status `color02`, unread `color01`, `accent`, online `#7dce6a`, away `#e0af68`). Every color except the rules is raised to at least 4.5:1 against the theme's `background` (WCAG AA for text): it moves towards white on a dark background and towards black on a light one, so its hue stays. Over the 122 themes on the development machine, all 120 that the client reads end at 4.5:1 or more. A theme change repaints the client within about a second, as in the bar. While Omarchy swaps the theme directory, or while a new theme file cannot be read, the previous colors stay and the file is tried again; after three tries without a readable theme, the client uses the terminal's colors, as at a start without one. A file that is not valid UTF-8 or has a color that is not six hex digits counts as unreadable.
  - A pane header and the tab strip show each friend's state with the friends bar's dot: online, the name in the foreground color and a green dot; away, the foreground and an amber dot; offline, the name in the name color, a gray dot and `offline` in the same gray. While the client is not online, the state is unknown, so the name keeps the name color and has no dot.
  - Like the bar's `parseSystemColors`, semantic names (`red`, `green`, `yellow`, `background`, `foreground`) are read first and `color0`–`color7` override them. 52 of 142 theme files on the development machine define only the semantic names.
  - Without Omarchy, the terminal's own ANSI palette is used.
- **Helper lifecycle:**
  - Without a running helper, the client starts `helper/omaq` detached, as the bar does. It first creates missing OmaQ home and state directories with mode `0700`; existing ones must already be private, otherwise it shows the helper's `chmod 700` advice. Helper start errors go to `helper.log` in the client's presence directory, and the last line is shown in the status line.
  - A `:quit` typed while the terminal answers the startup width query quits before any helper is started. A client that started a helper and quits before the handshake finishes the handshake first (at most 5 seconds), so the normal exit rules below decide. When the exit cannot be confirmed, because the handshake or the shutdown acknowledgement never came or another client still holds `exit.mutex`, the client never forces a stop. It prints that OmaQ may still be running.
  - Ownership requires the launch nonce: `omaq.protocol` must carry the client's `OMAQ_PROTOCOL_NONCE`, its child's pid and the handshake instance. A helper is stopped only when an `omaq-connect` started that instance (`started` marker with instance and nonce) and no other `omaq-connect` is alive.
  - The bar must also not be using it. When the client uses the bar's default state directory, it asks `omarchy-shell hancore.omaq status`; success or a timeout keeps the helper running.
  - When the last client process that started it exits, it sends `helper.shutdown_if_no_groups` and waits for the correlated acknowledgement; the helper cancels a shutdown whose requester disconnects first.
  - Group membership blocks the shutdown, and the client says so after leaving the screen.
  - A helper started by the bar or by anything else is never stopped, and the client never starts a competing helper while that helper restarts.
  - Instance tracking uses flock files in a presence directory per state directory, `$XDG_RUNTIME_DIR/omaq-cli/<scope>`, where the scope is the first 16 hex digits of the SHA-256 of the real state path, so clients of different state directories never count each other.
  - Exits take turns through `exit.mutex` in that directory. Each exiting client drops its own presence while it holds the mutex, so of two clients that quit together, the second still stops the helper.
- **The command:**
  - `omaq-connect --link` creates `~/.local/bin/omaq-connect` atomically, and only over a missing path or an existing OmaQ link. `--unlink` removes only OmaQ's link.
  - `install.sh` (live-root path) and `scripts/install-omaq.py` (source install) call `--link` after a successful installation and only warn on failure.
  - `scripts/uninstall-omaq.sh` removes the link after a successful plugin removal when it points to `…/hancore.omaq/cli/omaq.py` and its target is gone. A link to a still existing tree, or to anything else, stays.
  - Updating an existing installation does not create the link; run `~/.config/omarchy/plugins/hancore.omaq/cli/omaq.py --link` once.

## Structure

The client is one more presentation adapter on the helper socket. The helper stays authoritative for protocol, persistence, permissions and domain rules; the client sends ops, applies events and reuses the bar's wording.

- `cli/omaq.py` is the entry point. It loads `cli/omaq_connect/` by path, so it also works under `python3 -I`, and sets `sys.dont_write_bytecode` first, so no `__pycache__` lands in the plugin tree. It keeps `--link`, `--unlink` and `main()`.
- `cli/omaq_connect/` is a flat package with one job per module:
  - **State and rules:** `session.py` (`Conversation` and the friend rules), `chat.py` (`Chat`: conversations, pending messages, unread counts, read marks, history retries and clears), `files.py` (`FileTransfers` with `FileOffer` and `OutgoingSend`), `invites.py` (`Invites` with `Invite` and `PendingRequest`), `profile.py` (`Profile`: the own nickname), `identity.py` (`Identity`: the protection state, the identity actions with their request ids, timeouts and wording), `protocol.py` (limits, wording, `Message` and the passphrase rules) and `text.py` (widths, wrapping, sanitizing, emoji).
  - **Presentation:** `view.py` (`Screen` draws the frame from the app state), `modals.py` (`Confirmation`, `SecretPrompt`, `Help`, `Picker`, `FilePicker` and the `Overlay` classes; each modal handles its keys and draws its rows), `commands.py` (command, key and tip tables, command parsing, suggestions, `Completion`), `layout.py` (`Pane` with draft editing and recall, `Layout`), `keys.py` and `palette.py`.
  - **I/O adapters:** `link.py` (socket), `presence.py` (flock files), `helper_process.py` (paths and `HelperProcess`), `terminal.py` and `system.py`.
  - **Composition:** `app.py` holds `App`. It wires the objects, routes helper events and commands through two tables, keeps the input order (lock, passphrase line, help, confirmation, emoji picker, file list, overlay, reply choice), and runs the main loop, settle, exit and cleanup.
- The state and presentation modules never import `socket`, `termios`, `tty`, `subprocess`, `fcntl`, `select` or `signal`. `Chat`, `FileTransfers`, `Invites`, `Profile` and `Identity` reach the rest only through callbacks such as `send`, `say` and the friend list.
- `tests/cli_arch_test.py` checks this in `make test` and `make test-ci`. Each module may import only its listed neighbors, there are no cycles, and no module writes `from time import …` (or `os`, `subprocess`, `select`), because the tests patch those modules' attributes.

## Known open points

- **Races:** link creation and removal still have a check-then-act race, and the socket peer is not checked with `SO_PEERCRED`.
- **Width:** emoji widths follow the startup measurement. Regional-indicator flags and other multi-code-point sequences besides U+FE0F, ZWJ and skin tones are still measured per code point.
- **Group exits:** a group member's CLI-only exit keeps the helper online, and the note appears only after the screen is left.

## Stays out

- Group chats, creating and leaving groups, and contact removal.
- Calls, reactions, editing and deleting messages, and search. Edits and deletes made in the bar or by the peer are shown.
- The keyboard-and-hands visual.
